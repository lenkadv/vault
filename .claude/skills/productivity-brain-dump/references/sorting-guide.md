# Sorting Guide — 5-Bucket Heuristics

Most items sort themselves clearly. This guide is for the gray-area calls.

## The bucket definitions, sharpened

- **Tasks** — verb-led, doable in one sitting, no major decision required to start. Done has a clear definition.
- **Ideas** — possibilities. Could become projects later. Not ready to act on yet.
- **Decisions** — choices the user is sitting on. Two or more options where one needs to be picked.
- **Questions** — things the user doesn't know that they need to know. Answers come from research, asking someone, or looking something up.
- **Notes** — everything else worth keeping. References, observations, emotional content, things-to-remember.

## Common gray areas

### "Figure out my pricing"

Default to **Decision**. The verb "figure out" sounds like a task, but the work itself is choosing among options. If the user has zero options to choose from yet, it might be a Question ("what do other people charge?") that, once answered, will surface a Decision.

### "Research X"

If X has a clear use-case ("research best laptops to buy") → **Task** (research is the verb, the goal is a purchase decision later).

If X is open-ended exploration ("research AI agents") → **Idea** (it's a curiosity, not a job to be done).

If the user clearly wants an answer to one specific question ("research whether 401k withdrawals are taxable") → **Question**.

### "Maybe I should start a newsletter"

**Idea**. Anything starting with "maybe", "what if", or "could I" defaults to Ideas unless the user has clearly committed.

### "Talk to Sarah about the proposal"

**Task**. Verb-led, clearly doable.

### "I should probably call mom more"

This is on the boundary between Task and Note. Default to **Note** unless the user wrote "call mom this weekend" or similar with concrete intent. "I should probably X" is usually a self-observation, not a commitment.

### "Why does the dashboard keep crashing?"

**Question**. Even though the user might also need to do something about it, the immediate item is "I don't know why this is happening."

If they wrote "fix the dashboard crash" → **Task**.

### Emotional content with embedded action

"I'm freaking out about Friday and I haven't made the slides yet."

**Split it**:
- Note: "Freaking out about Friday" (preserve the worry)
- Task: "Make slides for Friday's presentation 🔥 [Work]"

The principle is: don't lose the emotional context AND don't lose the action. Capture both.

### Lists inside the dump

If the user writes "Things I need to do: X, Y, Z" — each of X, Y, Z is its own Task. Don't keep them as one lumped item.

### Multi-step projects

"Launch the newsletter" is too big to be a Task — it's a project. Default to **Idea** unless the user explicitly defined a first concrete step.

If they wrote "Launch the newsletter (first step: pick a name)" → keep "Pick a newsletter name" as the Task, file "Launch the newsletter" as the Idea/project context.

## When in doubt

When you genuinely can't decide between two buckets, pick the one that **respects the user's autonomy more**. Examples:

- Between Task and Idea → pick Idea. Putting something in Tasks implies commitment; Ideas is a holding pen. Better to under-commit than over-commit.
- Between Task and Decision → pick Decision. Tasks should be ready-to-do; if a choice is still needed, name it.
- Between any bucket and Notes → if it's genuinely unclear what the user wants from this item, Notes is the safe home.

## What the skill should NOT do

- **Don't drop items** just because they're short, weird, or don't fit cleanly. When unsure, file under Notes. The user trusts the skill to preserve their dump.
- **Don't merge items** that the user wrote separately. Each line/thought stays its own line in the output.
- **Don't editorialize.** If the user dumped something the skill thinks is a bad idea, file it as written. Not the skill's job to coach.
